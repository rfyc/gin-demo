# Go 线上问题排查修复

> **规范定位**: 本技能承载线上问题排查修复的流程规范（复现优先、根因优先、最小修复）。测试写法由 testing 承载，代码规范由 coding 承载，修复后的审查由 review 承载，本技能不重复这些内容。

## 激活时机

- 线上异常/报错需要排查修复（日志报错、接口 500、超时、数据错误等）
- 用户反馈线上功能不符预期、结果错误
- 监控/告警触发的线上问题处理

## 线上信息源（排查依据）

排查线上问题时，优先从以下信息源获取线上真实数据定位原因，不凭猜测推断线上状态：

- 线上只读 DB：`TODO: 线上只读库连接地址 / mcp 工具名`
- 线上日志查询：`TODO: 日志查询地址 / mcp 工具名`
- 其他信息源（监控面板、链路追踪等）：`TODO: 待补充`

> 待办项落地后替换 `TODO:` 占位；信息源不可用或权限不足时，向用户索要所需的线上数据（日志片段、查询结果），不臆测。

## 修复流程

按下述步骤顺序执行，上一步未完成不得进入下一步：

1. **明确 Bug**: 确认预期行为与实际行为的差异；信息不足（缺输入、缺报错、缺环境）时先向用户索要，不臆测
2. **写失败测试复现**: 按 testing 规范写一个会失败的测试（用触发 Bug 的输入，断言**预期正确**的结果），运行确认它确实失败——证明 Bug 真实存在且测试有效；无法稳定复现的 Bug 先与用户确认复现条件
3. **定位根因**: 先从「线上信息源」获取真实日志与数据（按报错时间/请求ID过滤），再沿调用链从报错点向上追（堆栈、`git diff`/`git log -S` 找近期相关改动、断点/打印中间值）；定位到根因再动手，禁止只修表象（如吞掉报错让测试变绿）
4. **最小修复**: 只改导致 Bug 的代码，不顺手重构、不扩大改动面；修复代码按 coding 强制规范编写（ctx 首参、错误包装、日志）
5. **验证**: 运行复现测试确认转绿；按 testing「测试命令」运行本次修改影响的相关包测试（含 `-race`），确认无回归；运行 `go build ./...`、`go vet ./...`
6. **防回归与审查**: 复现测试永久保留在测试套件中，防止同一 Bug 再次引入；调用 review 对本次修复变更全面审查，修复其发现的问题
7. **变更汇总**: 向用户汇报 Bug 根因、修复方式与验证结果

## 原则

- **复现优先**: 没有失败测试不算完成修复——「修复后测试通过」无法证明修复有效，只有「修复前失败 → 修复后通过」才能
- **根因优先**: 修复根因而非表象；发现多处同类问题（复制粘贴导致）时，逐一评估是否为同一根因，是则一并修复并在汇总中说明
- **最小改动**: Bug 修复的 diff 越小越易审查；发现的无关问题记录到汇总中，不夹带修复
